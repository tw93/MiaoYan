# MiaoYan Website Agent Guide

This is the website checkout on the `vercel` branch. The app source and its Xcode commands live on a different branch.

- `index.html`, `privacy.html`, `assets/`, and `data/` contain site content; `vercel.json` owns redirects.
- `scripts/build-site.py` generates the home pages from one copy table per language: `/` (English, the default) plus `/zh/`, `/tw/`, `/ja/`, `/ko/`, `/de/`, `/fr/` and `/es/`, the README's seven languages and the app's Spanish. Edit it and run `python3 -I scripts/build-site.py` instead of editing the generated `index.html` files; a copy change lands in every language in the same commit. The pages use `site.css`, which both generators inline into every page's head (rerun them after editing it), whose type and tokens follow mole.fit (one serif face: the Source Han subset ahead of Charter for Chinese, Charter ahead of Mincho for Japanese, whose curly quotes and ellipsis come back from the Mincho, as on mole.fit; Korean is the system sans with a serif wordmark, since iOS has no Myeongjo). The hero wordmark is near-black `MiaoYan 語` in every language, the family's one Traditional character per product (Mole 鼴, Kaku 書, Pake 殼, Hina 賞): 語 comes from the one-glyph `fonts/miaoyan-mark.woff2` that `scripts/build-fonts.py` cuts from Source Han Serif TC, with one small 荷叶绿 dot tracing a figure eight across it, counter-clockwise over 16s, with no drawn path. Near-black is 长石灰 `#363433` (2026-10-19), and the nav brand `MiaoYan` uses it rather than the green. Pages other than `/zh/` and `/tw/` show the English screenshots. The footer is mole.fit's dark band in MiaoYan's `--night`, as on the other product sites (maintainer 2026-10-18, after an ivory round): `MiaoYan · 語`, one about line, then Product / Help / Write / Convert / More Apps groups, with Mole's text steps. `privacy.html` and `404.html` are hand-written, but `build-site.py` rewrites their nav, footer and nav script from the English copy on every run (2026-10-19: both had shipped with a bare brand-only bar), so edit their body only.
- The blog lives at `/blog/` (English) and `/zh/blog/` (Simplified Chinese). Sources are `content/blog/index.json` (slug, date, modified, category, en and zh title and description) plus `content/blog/<slug>.en.md` and `<slug>.zh.md`; `python3 -I scripts/build-blog.py` writes `blog/`, `zh/blog/` (index, `<slug>/index.html`, `feed.xml`) and the marked blog blocks of `sitemap.xml` and `llms.txt`, taking the header, footer and scripts from `scripts/build-site.py`. Run it after `build-site.py`, then `python3 scripts/build-fonts.py` when a Chinese post changes, since the SC subset covers `zh/blog/` too; `build-blog.py --check` fails on stale output, an unknown category, a missing figure, a broken internal link or a download link. Categories are `writing` (pillar `markdown-editor-for-mac`) and `notes` (pillar `local-first-markdown-notes`); a new one goes into `CATEGORIES` and `CATEGORY_COPY` first. A post's cover is `img/blog/cards/<slug>.webp` (1600x900) and appears only once the file exists; `[[figure:<name>|<alt>|<caption>]]` embeds `img/blog/<name>.webp`, saved at twice its display width (the article column fills the page since 2026-10-21, as on every product site, and was 720px before). An h2 `FAQ` / `常见问题` with h3 questions becomes FAQPage data. Posts follow the site rule below: App Store and GitHub links only, never a Mac download.
- Release notes live at `/releases/` and `/zh/releases/` (maintainer 2026-11-08, as Mole, Hina and Pake have them), linked from the footer and from the last item of the home hero's trust row. `python3 -I scripts/build-releases.py --fetch` turns the GitHub releases into `data/releases.json`; after publishing a release run it, then the build steps in that script's docstring; `--check` fails on stale pages. Text outside a release's lists, install help and Japanese lists stay out; a version with no notes in the page's language shows the other language. The layout follows mole.fit's (Kata `rules/site.md`); the page turns the notes' `Mac:` and `iPhone and iPad:` prefixes into one heading per group, while GitHub and the App Store keep them inline. `.release` is a `section`, whose sitewide `margin-bottom: var(--gap)` collapses over the gap between versions unless it is reset.
- The Mermaid live editor (maintainer 2026-11-24, the first free tool page, plan in Kata `skills/seo/references/miaoyan-tools.md`) lives at `/tools/mermaid-editor/` and `/zh/tools/mermaid-editor/`; the other languages link the English page from the footer's Help column. It draws with MiaoYan's own Mermaid and theme, copied byte for byte from the app's `Resources/DownView.bundle/js/` into `assets/vendor/` with their hashes pinned in `scripts/mermaid_assets.py`, plus a small override there (`htmlLabels: false`, so a downloaded SVG reads the same on any computer and Safari can turn it into a PNG). Every Mermaid example in `content/blog/` (a mermaid block shown inside a four-backtick markdown fence) and every editor template (`content/tools/mermaid-templates.json`) is drawn ahead into `img/mermaid/<hash>.svg`, keyed by the code, the vendored files and the override; the blog shows each diagram under its source with a link that opens the code in the editor, and the editor's first paint is the default template's file, with Mermaid loading on focus or idle, never during a hover prerender. After changing an example, a template, the override or the vendored files: `python3 -I scripts/mermaid_assets.py`, `node scripts/render-mermaid.mjs` (Kata `scripts/site-shot/ensure.sh` first), then `build-tools.py` and `build-blog.py`; `mermaid_assets.py --check` fails on a changed vendored file, a stale manifest or a missing or orphaned SVG and only notes when the app's copies moved ahead, and `build-tools.py --check` fails on stale pages or a broken link. Share links carry the code after `#m=` (raw deflate, base64url; `#b=` without CompressionStream), so it never reaches a server, and GA's `page_location` drops the fragment; the last diagram stays in the browser's localStorage, as `privacy.html` says. Events: `tool_render` on the first diagram drawn after an edit, `tool_export` with `format`, `tool_copy` with `kind`.
- The Markdown table generator (maintainer 2026-11-25, the second tool) lives at `/tools/markdown-table-generator/` and `/zh/...`, built by the same `scripts/build-tools.py` shell, which every tool page shares: title, lede, the tool, the prose with its FAQ (drawn as the homepage's closed `<details>` by `fold_faq`, maintainer 2026-11-25: answers laid open read as a wall of text under the tool; FAQPage data is unchanged), then the one quiet MiaoYan block (outline App Store button) at the very end, so the tool's own primary button is the page's only filled one (maintainer 2026-11-25: the block read like an ad right under the tool). Its Markdown is written twice, by `table_markdown()` in Python for the first paint and by `assets/tools/markdown-table-generator.js` after any edit, and both must stay byte-identical: CJK, Hangul, full-width forms and most emoji count two columns (the same `WIDE` ranges in both), pipes are escaped unless already escaped. Pasting decides by content: a Markdown table always replaces the grid with its alignment; tab-separated text, then an HTML `<table>`, then CSV or semicolon text (two or more lines with the same field count, so a sentence with commas still pastes into one cell) replace the grid at the first cell or while it is untouched, and fill from the focused cell otherwise; each replace, delete and clear has one-level Undo. The last table stays in localStorage (`privacy.html` says so). Events: `tool_render` on the first edit, `tool_import` with `source`, `tool_copy`.
- The Markdown viewer (maintainer 2026-11-25, the third tool) lives at `/tools/markdown-viewer/` and `/zh/...`. The preview is an iframe holding MiaoYan's own preview stylesheets (`typography`, `theme-light`, `base`, `diagrams`) plus what the app's HTML export adds on top (16px, 760px centred, the export's code font stack), and the app's highlight.js and Mermaid draw into it, so a note reads as it does in the app; the stylesheets and highlight.js are byte copies of the app's `Resources/DownView.bundle`, pinned with their hashes in `scripts/app_assets.py`, whose `--check` also notes when the app's copy moved ahead. Two files come from npm instead: markdown-it 14.1.0 as the parser, since the app's cmark-gfm is native (the page says so rather than claim the app's parser), and KaTeX 0.16.47, taken from npm when the app's 0.16.0 let `\edef` expand past `maxExpand` (CVE-2024-28243) and one pasted formula froze the tab (review 2026-11-25); the app moved to the same 0.16.47 the same day (tw93/MiaoYan d84c5f56), so the two now match byte for byte. The iframe's sandbox has no `allow-scripts`: the page writes the parsed HTML in and Mermaid draws on the page, never inside the frame, so raw HTML in a note cannot run; any navigation that still moves the frame (an `<area>`, an SVG link, a form) reloads the srcdoc, and the exported HTML carries `script-src 'none'`. Math follows Pandoc: `$` opens before a non-space and closes after one, not before a digit or across a backtick; `$$` blocks never cross a blank line, and a start that found no end marks its lines so an unclosed `$$` on every line stays linear. The draft is saved only after a render finishes, so text that hangs the parser does not come back on reload. The post-parse steps mirror the app's `common.js` (task lists get `ul.cb`, tables a `.table-scroll`, headings an id from their text). Local image paths do not show and the FAQ says so. It is an editor as much as a viewer (maintainer 2026-11-25, after WeChat article editors such as doocs/md: 真正被用户所使用的工具), with the editing taken from MiaoYan rather than invented: Command-B, -I, -K, -E and Shift-Command-E as the app's Format menu with its carets (`TextFormatter.swift`; the app's Command-T belongs to the browser), Return continuing lists and quotes and ending them on an empty line as MiaoYanCore's `ListContinuation`, never inside a fence, and the word count as `noteWordCount` (one per CJK character, one per run of letters and digits, front matter left out). The panes scroll together both ways on block anchors, as doocs/md does: each top-level markdown-it block carries `data-line`, `md-highlight.js` wraps each source line in a span so `lineTops()` reads its wrapped top, and positions map along straight lines between pairs, with blocks past either pane's end folded into the end pair so the bottoms meet. WebKit runs no listener inside a frame whose sandbox lacks `allow-scripts`, the parent's own included (Chrome does), so in Safari the frame's `scroll` and `click` listeners never fire: preview-to-editor sync is driven from the page by reading the frame's scrollTop each animation frame while the pointer is over the frame, it has focus, or for a second after the pointer leaves (2026-11-25: the maintainer saw the Word page's preview not move the editor in Safari). Web links work there because `finish()` gives them `target=_blank`; do not add `allow-scripts` to fix the rest, since the frame holds raw HTML from any opened file. Phone width lays the iframe out at 375px (hidden at 560px and below). Copy (the primary action) carries each element's computed style inline, read from an offscreen clone in the frame, because WeChat, mail and CMS editors drop `<style>` and class; after doocs/md's `clipboard-dom.ts` the quote bar (an absolute `::before`, which WeChat strips) becomes a left border on a `<section>`, task boxes become ☐ and ☑, code whitespace becomes `&nbsp;` and `<br>`, nested lists follow their item, Mermaid SVGs become 2x PNGs shown at their size, and formulas go as TeX source, said in the status line (KaTeX needs its fonts, which a paste cannot carry). The Chinese page is the WeChat one (`wechat` in its data, labelled 复制到公众号): outside links, which do not open in a WeChat article, become numbered references at the end, a bare URL stays text and `mp.weixin.qq.com` links stay links; the English page keeps links. Export is also print to PDF, a self-contained HTML file with the stylesheets inlined (`data-line` stripped), and the Markdown itself (Command-S too). The last text stays in localStorage (`privacy.html`). Events: `tool_render`, `tool_import` (`source: file`), `tool_export` with `format` (`pdf`, `html`, `md`), `tool_copy` (`kind` `wechat` or `formatted`), `tool_fullscreen`.
- The Markmap editor (maintainer 2026-11-25, the fourth tool) lives at `/tools/markmap-editor/` and `/zh/...`. It draws with the app's own d3 6.7.0 and markmap-lib 0.14.1 plus markmap-view 0.14.0 (byte copies pinned in `scripts/app_assets.py`), in the app's depth colours (`ThemeColors.getMarkmapColors`) and its loader's spacing (20 / 20, padding 16), labels one line as in the app's `diagrams.css`. markmap-lib's built-in plugins would fetch Prism and KaTeX from jsDelivr, so the page drops the Prism plugin, empties the KaTeX plugin's asset lists and loads the site's own KaTeX when an outline has math; the site makes no CDN request. markmap-view binds wheel-to-pan on Macs at creation and ignores `scrollForPan: false`, so the page removes that listener: a plain wheel scrolls the page, a pinch or Ctrl+wheel zooms, dragging pans, and on touch one finger scrolls the page while two pinch the map. Labels go into the page itself, not a sandbox, so the transformer runs with `html: false` and the TeX markmap returns before KaTeX loads is escaped (review 2026-11-25: an `<img onerror>` in an outline ran on this origin and came back from the draft); a link in a label opens a new tab. Exports replace every foreignObject label with SVG `<text>` lines (a line per `<br>`, block or code-fence line; bold, italic, code, link and strikethrough runs; math as its TeX), size the viewBox from that copy and cap the PNG canvas at 16384 px a side and give the links `fill="none"` the dropped stylesheet held, because an image with foreignObject taints the canvas in Safari and other SVG readers do not draw it; PNG goes through a data URL. Copy Markdown writes a markmap fence longer than any backtick run inside. The last outline stays in localStorage (`privacy.html`), saved after a render. Events as the viewer, with `tool: markmap`. In WebKit a formula in a node shows as KaTeX's MathML (`site.css`, under `@supports (font: -apple-system-body)`, review 2026-11-25): WebKit paints KaTeX's positioned boxes inside a foreignObject from the map's corner, which the app fixed the same day (tw93/MiaoYan 5306a3e1, I-99). Chromium keeps the HTML, since MathML there sized the node short and a denominator crossed its line; the rules sit on `.markmap-foreign`, which is also the off-page box markmap measures in. Chromium tests cannot see this; `markmap-test` only checks Chromium keeps the HTML, and WebKit was checked with an offscreen WKWebView. A link carries an outline after `#m=` in the Mermaid editor's format (`mermaid_assets.payload`) and wins over the stored draft; the first edit drops the fragment (2026-11-25). Every markmap example in `content/blog/` (a markmap block inside a four-backtick markdown fence) shows under its source as `img/markmap/<hash>.svg`, the editor's own Download SVG, with a link that opens the outline in the editor; the hash is the outline's SHA-256, so after a new or changed example run `node scripts/render-markmap.mjs` (it also drops unused files), then `build-blog.py`, whose `--check` fails on a missing file. An offscreen WKWebView throttles timers, so an export there waits tens of seconds in `settled()`; that is the test window, not Safari.

- The Chinese typography cleaner (maintainer 2026-11-25, the fifth tool) lives at `/tools/chinese-typography-cleaner/` and `/zh/...`. `assets/tools/typography-cleaner.js` is a line-for-line port of the app's `Helpers/TypographyCleaner.swift` (Edit > Clean Typography, 清理排版 in the zh UI since V4.11.0) and must give the same bytes for any input: it works on grapheme clusters like Swift's `Character`, trims with Foundation's `.whitespacesAndNewlines` (which, unlike `Character.isWhitespace`, holds U+200B) and reads `isNumber` from a table of Swift's own numeric scalars, since `\p{N}` misses Han numerals and browsers ship other Unicode versions. `node scripts/check-typography.mjs` checks the port against `data/typography-fixtures.json` (the app's test strings plus a seeded corpus, cleaned by the compiled Swift); after the Swift changes, `--regenerate` (macOS with swiftc, the app's origin/main fetched) rebuilds the fixtures and the table, and a difference is fixed in the port, never by editing the fixtures. The result pane aligns lines (the cleaner only folds blank lines) and diffs each changed pair, marking new text and a removed space or blank line; a lone space kept between two changes counts as part of the change. A textarea turns CR into LF, so the page never cleans a CR; an opened file's CRLF endings and UTF-8 byte order mark are put back on download. Two known differences are kept on purpose (review 2026-11-25): Swift compares Characters by canonical equivalence, so U+037E reads as `;` and U+1FEF as a backtick there and not in the port, and neither occurs in Chinese writing; and three line shapes (a run of tens of thousands of spaces, backticks or `](`) clean in quadratic time in both, which only a pathological paste reaches. The result pane diffs at most 200,000 characters a render and marks the remaining changed lines whole. The last text stays in localStorage (`privacy.html`), and the page prose claims only what the port does.
- HTML and Word to Markdown (maintainer 2026-11-25, the seventh tool) lives at `/tools/html-to-markdown/` and `/zh/...`. `assets/tools/html-to-markdown-core.js` is a port of the app's `Helpers/HtmlToMarkdown.swift`, what the Mac app does with rich text pasted into a note (since V4.1.0, only when the HTML has a heading, list, table, quote or code block; the page always converts). `node scripts/check-html-to-markdown.mjs` runs it in Chromium against `data/html-to-markdown-fixtures.json` (the app's test HTML, a few clipboard shapes and 24 built blog bodies, converted by the compiled Swift); `--regenerate` rebuilds them after the Swift changes, and a difference is fixed in the port, never in the fixtures. The port is checked in `tidy` mode, which keeps two Foundation tidy bugs the page leaves out (tidy is HTML4, so `<figure>` and `<figcaption>` run together as `![a](x.png)caption`, and it keeps a comment's text, so `<!--EndFragment-->` lands in the note); outside that mode `prepare` also reads Google Docs' one `<b id=docs-internal-guid>` around a copy and its bold, italic and strikethrough written as span styles, and Word's `mso-list` paragraphs as nested lists, which the app turns into an all-bold note and `· item` lines (the app does not have this yet). The check also holds the page's own output for those shapes. The left pane is never the pasted HTML: paste, drop, `.html` and `.docx` all go through an allowlist rebuild (tags the converter reads, `href` and `src` with safe schemes, `alt`, `language-*` classes, `colspan`), so pasted scripts, handlers, frames and forms never reach the page, and the Markdown is read from that copy. A `.docx` is read by mammoth 1.13.0 (`assets/vendor`, pinned in `app_assets.py` with its BSD-2-Clause LICENSE prepended, loaded only when a Word file is opened); its embedded images, like data and file images in a paste, cannot come along and the status line counts them. Feishu is not named on the page: its clipboard HTML was never checked. Nothing is kept in localStorage.
- Markdown to Word (maintainer 2026-11-25, the eighth tool) lives at `/tools/markdown-to-word/` and `/zh/...`: the Markdown viewer's own tool (`viewer_page` with the slug, its own draft key and `tool` for events) led by Download Word, and the viewer gains the same button. The app has no Word export, so there is nothing to port: `exportDocx` in `markdown-viewer.js` takes the viewer's styled copy in `word` mode and hands it to docx 9.15.3's `htmlToContent` (`assets/vendor/docx-9.15.3.js`, its index, math and html builds joined behind the MIT LICENSE, pinned in `app_assets.py`, loaded on the first save). Word mode differs from the WeChat copy: lists stay nested, task boxes stay checkboxes (Word content controls), code keeps its own whitespace, links stay links, formulas go in as KaTeX's MathML (annotation removed) and become Word equations, a display formula alone in its block takes the block's place in a centred paragraph, and the copy is laid out at the page's text width (A4 on the Chinese page, Letter on the English one, one-inch margins: 601 and 624 CSS px) so tables and diagrams fit the margins. Fonts: `htmlToContent` writes the first family Word can have for every script and the preview stack starts with names Word does not know, so Word mode drops the text's font-family and sets Helvetica Neue with PingFang SC (eastAsia) in the document defaults and heading styles; code is Menlo. Web pictures are fetched (CORS, no credentials) for their bytes; refused ones and relative paths stay out and the status line counts them. Neither this Mac nor the test Mac has Word or Pages: the output is checked by rendering it to PDF with LibreOffice (`libreoffice-writer` and `libreoffice-math`, which equations need) on the devbox.
- Chinese fonts (maintainer 2026-11-08): Simplified reading text is Clear Han Serif, titles and Traditional stay Source Han Serif, all `font-display: block` with no `local()` and preloaded at high priority. After `python3 -I scripts/build-fonts.py` run it again with `--stamp`, which writes the `?v=` content hashes into `site.css`, then `build-site.py` and `build-blog.py`; `--check` fails on a stale hash or a non-blocking face.
- Tool pages run the window's full width (maintainer 2026-11-25: 全宽): `.wrap:has(> main.tool-page)` widens the page cap to `--tool-page` (1440px) and keeps a 32px side; beyond that the page centres, and the footer takes the same width and side at every size so its brand and the prose share one left edge (maintainer 2026-11-25, B of three candidates at 2333px, after the prose hugged the left of a wide display while the footer sat centred 635px in; rejected: centring the prose under a full-width tool, and moving only the footer left), the workspace fills the first screen (`--tool-h`, viewport minus 300px, 440px floor), and the prose and MiaoYan block below take the tool's full width (maintainer 2026-11-25: a 1000px reading column under the wider tool read lopsided on a wide display). `build-tools.py` `toolbar()` lifts each tool's actions into one row above the panes, its own controls on the left and the actions on the right as chips, the primary one filled, so nothing a tool does sits below the first screen. Panes that hold Markdown read as MiaoYan's editor (maintainer 2026-11-25: 预览页跟妙言的样式保持一致): paper `#FDFCF9`, ink `#403E3C`, the system pairing at 16px on a 23.8px line, tracked 0.02em, and the viewer, Markmap and typography inputs are coloured by `assets/tools/md-highlight.js` in the app's editor colours (`MarkdownRuleHighlighter.swift`: headings `#5E3DB3`, marks `#7A7872`, bold, strike and inline code `#9A7400`, link text `#24837B`, fences `#333`). It draws a `<pre>` behind a textarea whose letters are transparent, both on the same classes and widths so they wrap on the same characters; weights never change for the same reason, and setting `.value` from a script repaints too. The table generator sets its grid and its Markdown side by side above 880px. Both diagram panes fit below their zoom buttons and never under them: the Mermaid editor's `fit()` reads the frame's CSS padding (`.tool-preview` padding-top 58px), and the Markmap editor uses its own `fit()`, markmap-view's arithmetic up to its 2x ceiling centred in the part of the pane below the buttons, because markmap-view's `fit()` uses the whole pane and a tall map's top row ran under them. A 1x cap (as MiaoYan draws it) was tried and dropped the same day: the maintainer wanted the map to fill the pane (2026-11-25: 这里全屏会好很多); there is no `maxScale` option in markmap-view 0.14. Every tool has a full-screen switch at the end of its toolbar (maintainer 2026-11-25: 所有面板都可以全屏切换, `assets/tools/tool-shell.js`, loaded before each tool's own script): the tool becomes a fixed layer over the page, which is the only full screen an iPhone has, and also asks the Fullscreen API where it exists, so Esc or the system's exit leaves both; the panes take the height measured under the toolbar (`--full-h`, footer margin included), and a `resize` event tells the diagram panes to refit.
- Markdown to image, Markdown 转长图 (maintainer 2026-11-25, the tenth tool) lives at `/tools/markdown-to-image/` and `/zh/...`: the Markdown viewer's own tool (`viewer_page` with the slug, its own draft key and `tool`) led by Download image and Copy image, and opening at phone width, since a long picture is mostly read on a phone. It does what MiaoYan's Export > Image does (`MPreviewView+Export.swift` `exportImage`: the preview snapshot at twice its size, the note's title added as an h1 with the app's inline style when the text does not start with one; here the title is the opened file's name, and pasted text gets none). The viewer page itself does not get the button: a sixth action wrapped its toolbar to two rows at 1024px. A page cannot photograph itself, so `longImage()` lays the preview out again in a hidden same-origin frame (no scripts) at 375px (drawn at 3x, 1125px) or 840px (the 760px column with 40px sides, at 2x), with every stylesheet inline, `:root` rewritten to `html` (in an SVG image `:root` is the `<svg>`) and the dark media query pinned to the scheme the preview shows, then serializes it into an SVG foreignObject and draws that on a canvas. It must be a data URL: a blob URL taints the canvas in Chrome and in Safari, while a data URL reads back in both (checked 2026-11-25 in Chromium, Playwright WebKit and the system WKWebView), so the Markmap rule about foreignObject is about its own export, not this one. Nothing inside an SVG image loads from outside, so KaTeX's woff2 fonts and the note's pictures go in as data URLs, pictures fetched with CORS as for Word (resolved as the preview resolves them, so a path on this site comes along); one that cannot is left out and counted in the status line. Safari leaves those pictures blank on the first draw of a new SVG image, so the canvas is painted, then painted again 150ms later (decode() and a single later draw did not help in WebKit; modern-screenshot draws twice for the same reason). The scale drops in half steps until the canvas fits 32767px a side and 268M pixels (16.7M on iOS); past 1x the page says to split the text. Copy image hands `ClipboardItem` the image as a promise created inside the click, which Safari requires, and is hidden where the clipboard cannot take a PNG. Same-origin and third-party pictures are fetched like Word's, and Playwright WebKit reports a caught CORS failure as a page error, which tests must filter. Events: `tool_export` with `format: png`, `tool_copy` with `kind: image`.
- Markdown slides, 妙言 PPT on the Chinese page (maintainer 2026-11-25, the ninth tool), lives at `/tools/markdown-slides/` and `/zh/...`: MiaoYan's PPT mode in a page. The deck is its own page, `/tools/markdown-slides/deck.html` (written by `build-tools.py` `deck_page`, noindex, one copy for both languages), running `assets/tools/ppt-deck.js` with the app's reveal.js 4.3.1, its white and night themes, its Markdown and highlight plugins and KaTeX's auto-render and mhchem, all byte copies of the app's `Resources/DownView.bundle` pinned in `app_assets.py`. `ppt-deck.js` does what `ppt.html` does: `---` lines split slides as reveal's own separator (inside code fences too, as in the app), a leading `<!-- key: value -->` comment becomes reveal options, math is shielded first by a port of `Business/Markdown.swift`'s `protectMarkdownMath` (the code mask reads fences and indented blocks line by line where the app asks cmark), and one-element slides get `section-center`.
