# Notes, folders and files on disk

- Preserve recoverability for delete flows. Notes and attachments should move through the app Trash or system Trash path that matches the current context, not disappear through direct deletion.
- The app Trash is the library's own `Trash` folder (`Storage.checkLibraryTrash`), the one the iPhone and iPad app moves notes into too, so a note deleted on any device shows in every device's Trash (maintainer 2026-11-06); before that it was the volume's system Trash, iCloud's own `.Trash` for an iCloud library, which the other devices never saw. The folder is made by the first note delete, not at launch, and the sidebar shows the Trash row when the folder holds a note file even if none is loaded (`Storage.trashHasNotes`), since a note another device deleted is only on disk. Only notes go there: deleted folders and images still go to their volume's system Trash (`Storage.systemTrashDestination`), because the app Trash lists only the notes directly inside it and the iPhone's Empty Trash would erase a folder's notes nobody saw. Deleting from the app Trash hands the file to the system Trash, so it stays recoverable in Finder. Undo of a delete goes through `TrashReturn`, which moves a note back only if its Trash file is still the one that delete put there (the iPhone may have emptied the Trash and filled it with another note of that name) and the original path is free, and says so with a toast when one stays. Should a Trash project ever be the system Trash itself, calling `FileManager.trashItem` on an item already there renames it in place and makes it reappear: `Note.removeFile` marks it with `AppIdentifier.removedFromTrashKey` instead, and scans exclude that marker only inside Trash projects, so Finder recovery into a normal project remains visible.
- Pins follow a note in the iCloud Drive library to every device (`PinCloud` in MiaoYanCore, maintainer 2026-11-21): iCloud's key-value store holds the pinned notes' paths inside the ubiquity container's `Documents`, the App Store Mac app and the iPhone and iPad app share it as both are `com.tw93.miaoyan`, and the pin attribute (`AppIdentifier.pinKey`, a one-byte Bool) is still written beside it. Each device merges its own attribute pins into the store once (`PinsMergedIntoICloud` on the Mac), read from the files on disk rather than the notes loaded, and lays them over iCloud's first answer once; after that the store decides for every note in the container, so an unpin reaches the other devices. A note outside the container, and this repository's build, which has no key-value entitlement (`PinSync.hasKeyValueStore`), read the attribute alone. Every change of a note's URL goes through `Note.overwrite` or `Storage.relocateFolder`, which move the pins along; a new path that changes a note's URL another way must call `PinSync.cloud.moved` too. Undo of a delete moves the pin back in `TrashReturn.perform`, and a note leaving for good (deleted from the app Trash in `Note.removeFile`, or inside a folder deleted through `Storage.trashFolder`) calls `removed`, so a later note at that path does not come back pinned. Both sidebars delete folders only through `Storage.trashFolder`, which writes pending edits before the move. The store sync between devices needs a signed App Store build to check; tests cover the rules with a stand-in store.
- Treat iCloud sync and symlinked directories as file-system-sensitive surfaces; resolve paths deliberately and avoid loops or duplicate indexing.
- Wikilinks and backlinks depend on `Business/WikilinkIndex.swift`, note loading, search, and sidebar refresh behavior. Keep `[[note]]` parsing, recursive search, and Trash exclusions consistent.
- iCloud sync is iCloud Drive itself: the library is a folder in the app's ubiquity container (`UserDefaultsManagement.iCloudDocumentsContainer`), and `Storage` handles its `.icloud` placeholders. Verify fallback behavior when iCloud is unavailable.
- Trash handling spans `Business/Storage.swift`, `Business/Note.swift`, sidebar drag/drop, attachment cleanup, and system Trash fallback.
- `Note.loadFailed` (`readFailed || hasDamagedText`) marks a note whose file exists but could not be read (an iCloud placeholder offline, a permission error), or whose UTF-8 has invalid bytes, which `NoteText.decode` shows as U+FFFD rather than guessing another encoding; the editor shows `readOnlyNotice` for either. Its buffer does not hold the file's real bytes, so `executeSave` refuses every write until a read succeeds and the editor stays read-only for it. Never clear the flag without a successful read: saving that buffer is how an unreadable note used to be replaced by an empty file.
- A successfully removed note must retire its `Note` instance before any watcher, editor, lifecycle flush, or upload callback can save it again. Existing-note writes must fail closed if the file disappears, and UI rows may be removed only for filesystem operations that succeeded.
- Note bodies load only when a note is opened (and for Trash), so `note.content` is empty for most notes. Anything deciding whether a note refers to something reads unloaded bodies from disk: Clean Unused Attachments trashed every image of an unopened note until `Storage.findOrphanAttachments` did, and once any registered folder has an `i/` or `files/` it reads every note at any depth below every registered folder, whether or not that folder has one (a note one folder down links `../i/`, I-63; a note in a folder with no `i/` links another folder's), and the Trash the same way, a trashed note's links keeping their images by name. It enters each real directory once, skips a registered folder that is not on disk (the library's `Trash` before the first delete), and returns nil, cleaning nothing, when any note or subfolder cannot be read: a note iCloud keeps only online (`.name.md.icloud`, whose download it starts, every one in the same run) and a linked folder whose target is gone count as unreadable, a broken link to an image does not. Unlisted notes get one `Project` per folder.
- Version history lives in `Business/NoteVersionManager.swift` and `Controllers/VersionHistoryViewController.swift`; keep file IO off the main thread and UI updates on the main thread. Each row counts the lines it added and removed against the version before it (`+3 −1`), and the preview tints that version's new lines green and its rewritten lines yellow and scrolls to the first (`Helpers/VersionChanges.swift`, from quiet-md, 2026-11-21); the panel reads and diffs every version once on a background queue when it opens, and a pair longer than 20000 lines together is not diffed. All notes' versions together stay under 200 MiB (`NoteVersionManager.keepWithinBudget`, run when a run saves its first version or when the cached total plus the new version would pass the budget, so most saves skip the scan): the oldest go first across notes, never a note's newest one, and only folders and files named as a version (`isVersionFileName`) are counted or removed, so a symlink or a stray file in `Versions/` is left alone. Restore uses the text read when the panel opened, since another note's save may have dropped that file since.
- Directory symlinks are supported by storage scanning. Avoid recursion loops and duplicate notes when following symlinked directories. Match resolved filesystem paths rather than raw URL equality when reconciling directory entries with stored Project or Note instances: `/tmp` and `/private/tmp` aliases and directory hints can otherwise create twins after a move or rename.
- Folder moves use `Storage.moveFolder(_:to:)` in both sidebars. Only non-root folders may move within their current library, after pending saves succeed. Resolve destination symlinks, reject descendants, attachment/hidden/package folders and name conflicts, and use an exclusive same-volume rename. Preserve Note instances and version history, update the moved folder's parent, defer affected watcher events and note saves until disk and model paths agree, and let unrelated events continue. Quitting waits for the move to finish before the normal save flush.
- Note attachments follow the shared `i/` and `files/` convention (MiaoYanCore `AttachmentFile`, 2026-11-25): images live in an `i/` folder next to the note, referenced as `![](/i/<name>)`; videos and every other file in `files/`, a video written as an image (`![](/files/clip.mov)`, which `renderAttachmentMedia` in `renderMarkdownHTML` turns into a player) and any other file as a link named as it was picked (`[Report v2.pdf](/files/Report-v2.pdf)`), the file name kept to letters, digits, `-` and `_` (`AttachmentFile.normalizedName`). `/i/` and `/files/` are the note's folder, never the disk's root (`HtmlManager.isAbsolutePath`, I-98), and a preview click on a `/files/` link opens the file (`HtmlManager.noteAttachmentURL`). The iPhone and iPad app in MiaoYan-Pro writes and reads the same, so keep it stable.
- A new library starts with one guide folder (`GuideSeed` in MiaoYanCore: `妙言指南` for any Chinese language tag, `MiaoYan Guide` otherwise, three notes copied from `Resources/Initial`), written by whichever device opens the library first. The disk decides, not the loaded note list, which stops two folders down and skips notes iCloud has not downloaded: `GuideSeed.libraryHasNotes` walks the library, the Trash and `.icloud` placeholders included, and nothing is written when a note or a guide folder is there. The Mac decides once per install (`hasCreatedInitContent`), the iPhone once per device. The introduction ends with `miaoyan://guide/hide`, which the editor and the preview run in process (`AppDelegate.openGuideLinkInProcess`: LaunchServices could hand it to another installed copy). The Mac asks with the usual folder confirmation and moves the folder to the system Trash; the iPhone moves the three bundled notes to the library Trash and removes the folder when nothing else is in it, so the sentence beside the link names the guide and says it moves to the Trash, not that a whole folder does (`testTheIntroductionEndsWithTheLinkThatPutsTheGuideAway` holds the name). Left on purpose when the guide landed (`4bbe078a`): a guide put away on the Mac before any note was written leaves the library empty, so a device that opens it for the first time afterwards writes the guide again. Closing that needs a marker file in the user's library or a change to the Mac's folder delete.
- A Markdown file opened from Finder outside the library is an external project, and the sandboxed App Store build may read only that file, so images beside it need the user's own grant (#582, I-58). `Storage.folderNeedingAccess(for:)` answers only for an external note with local images whose folder cannot be listed; `ViewController.requestOpenedFolderAccess` then shows an open panel on that folder, at most once per folder per run when declined; `Storage.rememberOpenedFolder` keeps a security-scoped bookmark of the folder picked in `UserDefaultsManagement.openedFolderBookmarks` (the newest 20), and `startAccessingOpenedFolder` resolves them for a file at or under a granted folder on later launches. The direct-download build is not sandboxed and asks only when macOS itself refuses the folder. The SwiftUI shell does not ask yet.
